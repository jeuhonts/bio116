Data Atlas

Every gene, protein and structure you study lives as a record in a public database, identified by an accession (its ID) and stored in a standard file format. This tutorial follows one protein, human β-globin, through those databases, then teaches you to read the files they give you: FASTA, FASTQ, VCF, BED, PDB and mmCIF.

No single database holds everything about a protein. Each stage from gene to structure has its own specialist resource, and the records link to each other through their accessions. Click a stop to see where β-globin (gene HBB) lives at each stage and which file you would download.

Section 2

Databases: archives and curated collections

Biological databases come in two kinds. Knowing which kind you are using tells you how much to trust a record and whether it may contain duplicates.

Primary (archival)

What scientists submitted

  • Data deposited by the people who generated it
  • The submitter owns the record; the database rarely changes it
  • Many redundant and partial entries for the same gene
  • Complete and permanent: the scientific record

GenBank / ENA / DDBJ, SRA, PDB, EMDB, UniProtKB/TrEMBL

Secondary (curated)

What experts reviewed

  • Built from primary data by curators or careful pipelines
  • One reference record per gene or protein
  • Annotated with function, evidence and literature
  • The best place to start a question

RefSeq, UniProtKB/Swiss-Prot, Ensembl, InterPro, ClinVar, CATH

The biggest archives are shared by international partners that swap data every day, so a record submitted to one appears in all of them. INSDC links GenBank (USA), ENA (Europe) and DDBJ (Japan) for sequences. wwPDB links RCSB PDB, PDBe, PDBj, BMRB and EMDB for structures.

The main databases, by what they store

Decode an accession

An accession's shape usually tells you which database it came from and what kind of record it is. Paste one, or try an example.

Cite the versionRecords change. NM_000518.5 is version 5 of the record; NM_000518 means "whatever is current today". Write the full accession.version in your notes and methods so someone else can fetch exactly what you used.
Section 3

Sequence and genomics formats

Almost all sequence formats are plain text, so you can open them with head and search them with grep. What differs is the layout, and above all how each one counts positions.

FASTA: just the sequence

One header line starting with >, then the sequence, often wrapped at 60 characters. The header is free text, but big databases use fixed layouts. This is the UniProt header for β-globin:

FASTQ: reads with quality scores

Sequencers report how sure they are of every base. FASTQ stores each read as four lines, and the fourth line holds one quality character per base. The character's ASCII code minus 33 is the Phred score Q, and the chance the base is wrong is 10−Q/10. Q30 means 1 error in 1,000, the usual bar for "good". Hover or tap a base.

GenBank flat file: the annotated record

      
A full record with a header, a feature table and the sequence at the end. Keywords start at column 1, and features use 1-based, inclusive coordinates: a coding sequence from base 100 to base 540 is written CDS 100..540. The layout, simplified:

DEFINITION  Homo sapiens hemoglobin subunit beta (HBB), mRNA.
ACCESSION   NM_000518
VERSION     NM_000518.5

FEATURES             Location/Qualifiers
     gene            1..end
                     /gene="HBB"
     CDS             start..stop
                     /gene="HBB"
                     /protein_id="NP_000509.1"
                     /translation="MVHLTPEEKSAVTALWGKVNVDEVGGEALGRLLVVYPWTQRFFE..."

0-based or 1-based? The most common bug in genomics

      
GFF, VCF and SAM number the first base 1 and include both ends. BED numbers the gaps between bases from 0 and excludes the end. The same bases get different numbers, so converting between formats is where off-by-one errors creep in. Choose a region to see both.

      

        

          
          
        

        

        

      

    


    
    

      
Section 4
Structure formats

      
A structure file is a list of atoms with x, y, z coordinates in ångströms (1 Å = 0.1 nm), plus metadata about how the structure was determined. The method decides what you can trust.

      

        

          
MethodWhat was measuredQuality to checkWhere the data goes

Cryo-EMimages of frozen particles, averaged into a 3D density mapresolution (Å), map–model fitmap in EMDB, model in PDB

            
NMRdistances and angles in solutionrestraint violations; files hold an ensemble of modelsmodel in PDB, data in BMRB

            
Prediction (AlphaFold)nothing: computed from sequencepLDDT per residue, PAE between residuesAlphaFold DB, not the PDB

          
        

      

      
For X-ray and cryo-EM, smaller numbers are better. Around 1.5 Å you can see individual atoms. At 2–2.5 Å side chains are clear, at 3–3.5 Å the backbone is reliable but side chains are guesses, and beyond 4 Å you mostly see the overall shape. 4HHB, deoxyhaemoglobin, was solved at 1.74 Å.


      
The PDB format: fixed columns

      
The original PDB format is 80 characters per line, and every field lives at fixed column positions. ATOM lines hold standard residues, while HETATM lines hold everything else: ligands, metals, water. PDBx/mmCIF: the current standard

      
The fixed columns caused hard limits: at most 99,999 atoms, one character per chain ID, and 4-character entry IDs. Ribosomes and viruses don't fit. Since 2014 the master format of the PDB archive has been PDBx/mmCIF, where each value is named and tables are written as loop_ blocks with no column limits. Very large structures are only available as mmCIF. The same atom as above:

_refine.ls_d_res_high      1.74
#

_atom_site.label_atom_id
_atom_site.label_comp_id

Key-value pairs hold single facts, such as the method and the resolution.

          
A loop_ is a table: first the column names, then one row per atom, separated by spaces.

          
Two numbering schemes. label_ columns are the archive's own consistent numbering. auth_ columns are what the authors used, and match papers and the old PDB format. When residue numbers in a paper don't match your file, check which scheme your software shows.

          
Abridged: real files have many more categories and columns. Values match the illustrative ATOM line.

        

      


      
Predicted structures: read the B-factor column differently

      
AlphaFold DB models use the same PDB and mmCIF formats, but the B-factor column holds the pLDDT score (0–100): the model's confidence in each residue. Viewers colour by it with this standard scale. The PAE (predicted aligned error) comes as a separate JSON file and tells you whether domains are placed correctly relative to each other.

      

        
> 90Very high: trust side chains

        
70–90Confident: backbone is good

        
50–70Low: treat with caution

        
< 50Very low: often a disordered region

      

      
Density maps from cryo-EM are stored separately in EMDB as 3D grids of numbers (MRC/CCP4 format, .map). Open them in a viewer such as ChimeraX, not a text editor.


      
From the command line

      
Because PDB fields sit at fixed positions, cut them by character position with cut -c. Splitting on spaces with awk breaks when numbers run together: a line containing -10.123-20.456 has no space between the two coordinates.

      
# how many atoms, and how many α-carbons?
grep -c '^ATOM' 4HHB.pdb
grep '^ATOM' 4HHB.pdb | cut -c 13-16 | grep -c ' CA '
# which ligands and how many atoms each (heme is HEM, water is HOH)
grep '^HETATM' 4HHB.pdb | cut -c 18-20 | sort | uniq -c
# the chains in the file
grep '^ATOM' 4HHB.pdb | cut -c 22 | sort -u

    


    
    

      
Section 5
Getting the data

      
Every database has a website for browsing and a web address pattern for downloading. Downloading from the command line means you can record exactly what you fetched and repeat it for a hundred IDs with a loop. curl -o name URL saves a URL to a file.

      

      
For raw sequencing runs, use the SRA Toolkit (fasterq-dump SRR1039508) or ENA's file browser, which links straight to compressed FASTQ files.

      
Good practice

      
    
        
  1. Record the full accession.version and the date or database release of everything you download.
    2. 
        
  2. Keep downloaded files unchanged in data/raw/. Write everything you derive from them to results/.
    3. 
        
  3. Save the download commands in a script, so the data can be fetched again.
    4. 
        
  4. Check large downloads against published checksums with md5sum.
    5. 
        
  5. Cite the databases you used. Most list the paper to cite on their website.
    6.
